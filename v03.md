## 0. Executive Summary & Architectural Contract

The Wazir V02 architecture established the **Autonomous Execution Control Plane** — defining artifact provenance, execution recovery, basic test intelligence, process sandboxing, and resource governance.

**Wazir V03** evolves Wazir into an **Autonomous Software Delivery and Fleet Verification Platform**. Synthesizing key architectural mechanics from enterprise autonomous delivery systems (such as the Harness SDLC platform), V03 adapts continuous verification, outbound delegate networking, AST call-graph test slicing, streaming log sanitization, hierarchical VRAM partitioning, declarative Policy-as-Code, cryptographic supply chain attestation (SLSA/Cosign), and reversible database migrations specifically for distributed multi-agent coding fleets.

### 0.1 Non-Negotiable Architectural Rules (V03 Extension)

1. **Autonomous verification precedes all branch merges.** No agent-generated patch or branch may merge into `main` without passing both targeted test suites and continuous verification telemetry checks.
2. **Workers are strictly outbound.** Remote fleet computers (Delegates) initiate outbound connections via mTLS/WebSockets. No inbound listening ports are exposed on runner machines.
3. **Zero plaintext secret propagation.** Secrets are injected in-memory at execution time. Streaming output interceptors redact tokens, keys, and credentials before data hits disk, `Block` history, TUI logs, or model contexts.
4. **AST call-graph slicing gates intermediate test cycles.** Iterative agent loops (`Plan → Implement → Test → Repair`) must execute only tests impacted by the delta. Full test suites run only on root architectural modifications or final pre-merge gates.
5. **Interactive tasks preempt batch agents.** The resource governor partitions hardware capacity; high-priority interactive tasks (`wa ask`, `wa chat`) take precedence over background fleet refactoring jobs.
6. **Database schema migrations require verified reversals.** Any task modifying database schemas (Prisma, Drizzle, Flyway) must supply and successfully execute an automated down/undo migration in an isolated ephemeral database.
7. **Every agent commit carries an immutable, cryptographically attested SLSA provenance record.** Commits must be verifiable against model digest, prompt hash, sandbox policy decision, and tool execution logs via Cosign.
8. **Policy evaluations are declarative and versioned.** Static authorization is superseded by Open Policy Agent (OPA) / Rego policies evaluated at three distinct lifecycle hooks: `OnTask`, `OnTool`, and `OnMerge`.

## Phase 1: Continuous Verification & Anomaly Rollback Engine

### 1.1 Objective
Ensure that code generated by autonomous agents is not only syntactically correct and unit-tested, but runs stably without runtime exceptions, performance regressions, or metric anomalies. If anomalies are detected, the system deterministically rolls back the agent's worktree and feeds structured telemetry back into the repair loop.

### 1.2 Data Schemas (`packages/evaluation/src/types/verification.ts`)

```typescript
export type AnomalySeverity = 'low' | 'medium' | 'high' | 'critical';

export interface TelemetryMetricSnapshot {
  timestamp: string;
  durationMs: number;
  cpuPercent: number;
  memoryBytes: number;
  errorCount: number;
  exitCode: number;
}

export interface MetricBaseline {
  metricName: string;
  mean: number;
  stdDev: number;
  sampleCount: number;
  p95: number;
}

export interface AnomalyEvent {
  metricName: string;
  severity: AnomalySeverity;
  observedValue: number;
  baselineMean: number;
  sigmaDeviation: number;
  clusterSignature?: string;
  rawSample: string;
}

export interface VerificationResult {
  passed: boolean;
  score: number; // 0.0 - 1.0
  anomalies: AnomalyEvent[];
  rollbackTriggered: boolean;
  rollbackReason?: string;
  telemetry: TelemetryMetricSnapshot;
  verifiedAt: Date;
}
```

### 1.3 Continuous Verification Engine (`packages/evaluation/src/continuousVerification.ts`)
- **Metric Verification**:
  - Compares test/smoke runtime metrics against historical baselines.
  - Configurable sensitivity thresholds:
    - **1-sigma (High Sensitivity):** Flags any deviation > 1 standard deviation for critical services.
    - **2-sigma (Standard):** Flags standard latency and memory regressions.
    - **3-sigma (Tolerant):** Catches catastrophic performance drops.
- **Log Event Clustering**:
  - Intercepts stderr and application logs during verification.
  - Normalizes log lines by removing timestamps, UUIDs, memory addresses, and file line numbers to extract the underlying error signature.
  - If a novel error cluster is observed that does not exist in the baseline, the deployment is marked as failed regardless of numerical metrics.
- **Automated Worktree Rollback**:
  - Invokes `WorktreeManager.rollback(worktreePath)` to restore the branch to the base commit.
  - Synthesizes a structured `RepairPrompt` containing the anomaly signatures and passes it to the `CodingAgent` for an automated fix attempt.

### 1.4 CLI Commands
```bash
wa verify run <execution-id> [--sensitivity high|medium|low]
wa verify baseline show [--service <name>]
wa verify status <job-id>
```

### 1.5 Verification Criteria (Gate 11)
- [ ] Artificially injected memory leaks or latency spikes trigger automated worktree rollback.
- [ ] Novel error signatures in stderr fail verification even when exit code is 0.
- [ ] Clean verification runs record a baseline entry without altering worktree state.

## Phase 2: Wazir Delegate & Fleet Outbound Networking

### 2.1 Objective
Replace the polling-based SSE task loop with an enterprise-grade, outbound-only Delegate protocol over secure WebSockets (TLS) with cryptographically verifiable delegate tokens and instant revocation.

### 2.2 Data Schemas (`packages/core/src/types/delegate.ts`)

```typescript

export interface DelegateSession {
  delegateId: string;

  status: DelegateStatus;
  capabilities: DelegateCapabilities;
  activeTasks: string[];
  connectedAt: Date;
  lastHeartbeat: Date;
  latencyMs: number;
}
```

### 2.3 Networking & Delegate Engine (`apps/api/src/services/delegateServer.ts` & `apps/worker/src/delegateClient.ts`)
- **Outbound-Only Connectivity**:
  - Remote fleet runners initiate an outbound connection to `wss://<control-plane>/v1/delegate/connect`.
  - Zero inbound ports required on target machines or GPU worker nodes.
- **Heartbeat & Liveness**:
  - 15-second heartbeat interval with jitter.
  - If 3 consecutive heartbeats are missed, the control plane marks the delegate as `disconnected` and triggers execution recovery for all assigned tasks.
- **Dynamic Token Revocation**:
  - Delegate tokens are validated during the initial handshake.
  - When `wa delegates revoke <id>` is invoked, the control plane immediately terminates the WebSocket connection and rejects reconnection attempts.
- **Minimal Image Footprint**:
  - Standard worker and minimal runner variants with hardened AppArmor/seccomp profiles.

### 2.4 CLI Commands
```bash
wa delegates list [--json]
wa delegates token create --name <name> [--expires <duration>]
wa delegates token revoke <token-id>
wa delegates inspect <delegate-id>
```

### 2.5 Verification Criteria (Gate 12)
- [ ] Workers behind NAT/firewalls connect successfully without inbound port forwarding.
- [ ] Revoking a token terminates active worker connections within 1 second.
- [ ] Worker disconnection triggers `ExecutionRecoveryCoordinator` without task duplication.

## Phase 3: Production AST Test Intelligence

### 3.1 Objective
Accelerate the inner coding loop of agents by dynamically analyzing Git commit deltas and code call graphs, selecting and executing only the unit/integration tests directly affected by the changes.

```typescript
  impactedSymbols: ImpactedSymbol[];

```

### 3.3 Engine Implementation (`packages/evaluation/src/testIntelligence/`)
- **Git Delta Parser**:
  - Extracts modified files and changed line ranges (`git diff -U0`).
- **AST Dependency Grapher**:
  - Uses TypeScript Compiler API / Babel parser to parse source files and extract exports, imports, and function call hierarchies.
  - Builds an in-memory directed dependency graph (`A imports B`, `TestX imports ClassA`).
- **Impact Analysis & Selection**:
  - Maps modified symbols to test files that directly or transitively depend on them.
  - Automatically includes any newly created or modified test files.
- **Root Override Guard**:
  - If changes touch core configuration files (`package.json`, `tsconfig.json`, `pnpm-workspace.yaml`, `.env.example`), the engine skips slicing and triggers the full test suite to prevent cascading breakages.

### 3.4 CLI Commands
```bash

wa test run [--intelligence] [--full]
```

### 3.5 Verification Criteria (Gate 13)
- [ ] Modifying a single method executes only tests covering that method and its dependents.
- [ ] Modifying root package configurations forces execution of the entire test suite.
- [ ] Test execution time is reduced by at least 70% on targeted feature patches.

## Phase 4: Streaming Log Sanitization & In-Memory Secret Brokerage

### 4.1 Objective
Prevent accidental leakage of sensitive credentials, API keys, private keys, or passwords by intercepting subprocess output in real time and replacing secrets with redacted placeholders before they reach disk, TUI history, or LLM context windows.

### 4.2 Data Schemas (`packages/core/src/types/sanitizer.ts`)

```typescript
export interface RedactionRule {
  id: string;
  name: string;
  pattern: RegExp;
  mask: string;
  highEntropyDetection: boolean;
}

export interface SanitizationResult {
  originalLength: number;
  sanitizedLength: number;
  redactionsCount: number;
  detectedRuleIds: string[];
  clean: boolean;
}
```

### 4.3 Streaming Sanitization Engine (`packages/core/src/services/streamingSanitizer.ts`)
- **Real-Time Stream Interception**:
  - Implements a Node.js `Transform` stream that wraps stdout/stderr of sandboxed worker tool processes (`bwrap`).
  - Processes chunks with a sliding window buffer to catch secrets that span chunk boundaries.
- **Multi-Tier Detection**:
  - **Static Rules:** Regular expressions for known credential formats:
    - AWS Access Keys (`AKIA[0-9A-Z]{16}`)
    - GitHub PATs (`ghp_[0-9a-zA-Z]{36}`)
    - Anthropic / OpenAI keys (`sk-ant-[a-zA-Z0-9_-]{32,}`, `sk-[a-zA-Z0-9]{32,}`)
    - JWT tokens (`eyJ[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.?[A-Za-z0-9-_.+/=]*`)
    - Private Key Blocks (`-----BEGIN [A-Z ]+ PRIVATE KEY-----`)
  - **Dynamic Injected Secrets:** Every secret provisioned from the Secret Broker is registered as a dynamic literal mask during task execution.
- **Context & Storage Sanitization**:
  - Masked text (`[REDACTED_SECRET:<RULE>]`) is what gets written to `Block.stdout`, persisted in PostgreSQL/JSON, and fed into the `ContextCompiler`.

### 4.4 CLI Commands
```bash
wa secrets test-redaction "<input-string>"
wa secrets rules list
wa secrets audit [--execution-id <id>]
```

### 4.5 Verification Criteria (Gate 14)
- [ ] `printenv` or `echo $SECRET` inside a tool execution produces masked tokens in `Block` history.
- [ ] Splitting tokens across stream chunks still results in 100% redaction.
- [ ] Context compiler token counts reflect sanitized strings without secret exposure.

## Phase 5: Hierarchical Resource Governor & Priority Partitions

### 5.1 Objective
Manage finite hardware resources (GPU VRAM, CPU cores, memory, and LLM inference concurrency) across concurrent interactive and background fleet tasks, preventing resource starvation and system out-of-memory (OOM) failures.

### 5.2 Data Schemas (`packages/scheduler/src/types/governance.ts`)

```typescript
}
```

### 5.3 Governor Implementation (`packages/scheduler/src/governance/resourceGovernor.ts`)
- **Dual-Partition Architecture**:
  - **Interactive Partition:** Reserved for `wa ask`, `wa chat`, and immediate user commands. Holds reserved VRAM and preempts lower-priority queues.
  - **Batch Fleet Partition:** Allocates remaining compute to background agents (`wa jobs`). Throttled automatically when interactive capacity demands rise.
- **VRAM Lease Tracking**:
  - Tracks model footprint on local runtimes (Ollama / LM Studio / vLLM).
  - Tasks request a VRAM lease before loading large models; if insufficient memory exists, tasks queue gracefully instead of triggering CUDA out-of-memory errors.
- **Hierarchical Timeout Propagation (`EXPIRE_ALL`)**:
  - Step, stage, and task timeouts. If a stage timeout expires, running child tool processes are immediately sent `SIGKILL` and intermediate worktrees are purged.

### 5.4 CLI Commands
```bash

wa resources vram status
wa resources queue list
```

### 5.5 Verification Criteria (Gate 15)
- [ ] High-priority interactive requests jump to the head of the queue over active batch tasks.
- [ ] VRAM reservations prevent concurrent 70B model loads on single-GPU hardware.
- [ ] Stage timeouts abort all nested child tool executions cleanly.

## Phase 6: Declarative Policy-as-Code Engine (OPA / Rego)

### 6.1 Objective
Replace static rule checks with declarative, version-controlled Policy-as-Code using Open Policy Agent (OPA) and Rego. Policies evaluate structured JSON state across three mandatory lifecycle hooks: `OnTask`, `OnTool`, and `OnMerge`.

### 6.3 Policy Engine Architecture (`packages/policies/src/opaEngine.ts`)
- **Embedded OPA Evaluator**:
  - Integrates `@open-policy-agent/opa-wasm` for fast, in-process Rego evaluation without external daemon dependencies.
- **Lifecycle Hook Enforcement**:
  1. **OnTask:** Evaluates whether a prompt or target model violates organization usage rules or budget limits.
  2. **OnTool:** Evaluates every individual shell, file, or network invocation before spawning child processes.
  3. **OnMerge:** Evaluates git diffs before merging worktrees back into `main`. Blocks unauthorized modifications to root configurations, credentials, or workflow files.
- **Git Experience for Policies**:
  - Policies are stored in `.wazir/policies/*.rego` within the workspace and versioned alongside project code.


- [ ] Attempting to modify `.wazir/policies/` or root workflow configs in a worktree triggers an `OnMerge` policy rejection.
- [ ] Rego policies evaluate within < 5ms per evaluation hook.

### 7.3 Attestation Engine (`packages/core/src/services/provenanceAttestor.ts`)
- **SLSA Generation**:
  - Computes cryptographic SHA-256 digests of all patch files and git commits generated during a task.
  - Bundles execution metadata into a standard in-toto SLSA v1 statement.
- **Cosign Cryptographic Signing**:
  - **Keyless Signing (OIDC):** Authenticates via OIDC provider to obtain ephemeral signing certificates recorded to the Rekor transparency log.
  - **Local / KMS Key Signing:** Signs artifacts using asymmetric Ed25519/ECDSA key pairs stored in the Wazir Secret Broker.
- **Verification Gate**:
  - `wa provenance verify <commit>` validates that the signature matches the commit hash and that the originating model and execution environment were authorized.

### 7.4 CLI Commands
```bash

```

### 7.5 Verification Criteria (Gate 17)
- [ ] 100% of merged agent commits include an attached and valid in-toto SLSA statement.
- [ ] Tampering with a single byte in an agent-generated patch causes verification to fail.
- [ ] Signed provenance statements successfully validate against Cosign CLI.

## Phase 8: Database DevOps & Reversible Migrations

### 8.1 Objective
Ensure that autonomous agents making full-stack application changes do not corrupt or desynchronize databases. Automatically verify that database migrations generated by agents (Prisma, Drizzle, TypeORM, Flyway) are strictly reversible through automated undo checks in isolated containers.

### 8.2 Data Schemas (`packages/database/src/types/migrationDevOps.ts`)

```typescript
export type MigrationFramework = 'prisma' | 'drizzle' | 'typeorm' | 'flyway' | 'liquibase' | 'raw_sql';

export interface MigrationFilePair {
  framework: MigrationFramework;
  migrationName: string;
  upPath: string;
  downPath?: string;
  isReversible: boolean;
}

export interface ReversibilityVerificationResult {
  passed: boolean;
  framework: MigrationFramework;
  appliedCount: number;
  revertedCount: number;
  schemaDiffClean: boolean;
  executionLogs: string[];
  error?: string;
}
```

### 8.3 Migration Reversibility Engine (`packages/database/src/migrationValidator.ts`)
- **Migration Detection**:
  - Automatically identifies new or modified migration files in the agent's worktree.
  - Detects if an accompanying down/undo migration is missing and prompts the agent to generate it.
- **Ephemeral Container Verification**:
  - Spawns a clean, disposable database container (PostgreSQL / MySQL) in Docker.
  - Executes the full lifecycle validation sequence:
    1. Run initial migrations up to the base commit.
    2. Apply the agent's new migration (`migrate_up`).
    3. Verify schema state and health.
    4. Execute the undo migration (`migrate_down`).
    5. Diff the resulting schema against the initial state; any residual tables, columns, or types fail the gate.
    6. Re-apply `migrate_up` to verify repeatability.

### 8.4 CLI Commands
```bash
wa db-devops verify [--worktree <path>]
wa db-devops inspect-migrations
```

### 8.5 Verification Criteria (Gate 18)
- [ ] Migrations lacking an undo mechanism fail verification.
- [ ] Schema drift after a `migrate_down` cycle triggers a hard failure and halts the merge.
- [ ] Disposable database containers are cleanly reaped post-verification with zero socket leaks.
