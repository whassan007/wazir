## Key design decisions
- **Home**: `packages/assurance` (`@wazir/assurance`) holds all trust-critical WFA logic. Core gets only generic additive hooks (task `role`, `TaskType 'verification'`, `toolCapabilities`, FORMAL evidence kind) so core never depends on WFA.
- **Verdicts**: Only `verdict.ts` produces final verdicts. Adapters return native outcomes. The documented rules match the C0 code: trusted-base gaps take PROVED down to BOUNDED_PASS, a missing or failed probe gives INCONSISTENT_ASSUMPTIONS, and the gate needs at least one formal pass.
- **Write fencing**: There are two layers. Layer A makes `specs/` read-only in the worktree (chmod, plus a sandbox ro-bind where available) and adds a policy `deny` rule `spec-write-fence-deny`. Layer B extends `VerifiedIntegrationCoordinator` oracle protection to `specs/**`, allowing it only when the persisted task role is `spec-author`.
- **Scheduling**: Verification tasks bypass `routeModel` through a new `scheduleToolHost`. It shares the `scheduleComputer` feasibility path, with `tool:*` capabilities matched against `Computer.capabilities`. Heavy campaigns prefer DGX/GX10-class hosts. If no host is feasible the result is `NOT_RUN`.
- **Repair**: `AssuranceReplanner` implements the existing `TaskReplanner`. Regressions persist under `.wazir/assurance/regressions/`, the attempt limit `k` comes from config, and VerifAI holdout seeds are partitioned from the spec hash.
- **Ledger**: Append-only JSONL with a sha256 chain over canonical JSON. Appends are fenced by the `ExecutionEngine` lease epoch/token and must match the current workspace revision.
