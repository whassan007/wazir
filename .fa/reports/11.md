# Agent 11 — Spec registry and promotion rules

Implemented `packages/assurance/src/registry.ts` using the C0 contracts and FORMAL_ASSURANCE.md §2.2. Shared exports and other agents' paths were not edited.

- Recursive, deterministic discovery of JSON/YAML manifests under `specs/` by default, with per-ID/version storage and duplicate revision rejection.
- Runtime manifest validation and canonical SHA-256 hashing: recursively sorted object keys, preserved array order, excluding only the root `content_hash`. Loading rejects integrity mismatches.
- Agent creation accepts only drafts without reviewers. Lifecycle permits draft → reviewed → approved → retired, plus retirement of draft/reviewed revisions. Retired revisions cannot be revived.
- Generic promotion cannot approve specs. `approveSpec` requires a reviewed revision, named reviewer and explicit nonempty approval token, or a structured proof identifying the same human actor. Approval records the reviewer and rehashes the revision.
- Release checks fail closed with `SPECIFICATION_REVIEW_REQUIRED` for nonapproved, malformed, unreviewed or hash-mismatched manifests. `canGateRelease` returns the corresponding boolean.
- Registry inputs and outputs are cloned to prevent mutation through retained references.

Validation: `npx vitest run packages/assurance/src/__tests__/registry.test.ts` — **48/48 passed**. `npx tsc --build packages/assurance` — passed.

Integration boundaries: Neither `yaml` nor `js-yaml` is installed, so YAML support intentionally covers mapping/sequence/flow collections and plain/quoted scalars, rejecting unsupported constructs such as multiline scalars, tags and anchors. JSON supports the complete manifest shape. Directory loading reads existing versioned manifests; mutation methods update the in-memory registry, and persistence/version-control remains the caller's responsibility. A bare `getSpec(id)` selects the last loaded/inserted revision; pass an explicit version when binding evidence. Approval proof authentication must happen in Wazir's existing approval gate before calling `approveSpec`; a nonempty token is an explicit approval input, not cryptographic proof of identity. Loaded approved revisions rely on the reviewed version-controlled store as their authority. Worker write fencing belongs to the policy/worktree integration and was not changed in this owned-path task.
