# Agent 12 — Spec write fencing in the policy engine

Implemented and verified spec write fencing across `@wazir/core`, `@wazir/policies`, and `@wazir/assurance` (per `FORMAL_ASSURANCE.md` §2.2, `DESIGN.md` §1.5, and `DESIGN_REVIEW.md` findings 2–3).

## Summary of Changes

1. **Layer A — PolicyEngine (`packages/core/src/services/policyEngine.ts`)**:
   - Added role-aware specification write fencing (`spec-write-fence-deny`) and human-only approval fencing (`spec-approval-human-only-deny`).
   - Only executions whose trusted, persisted task role is `'spec-author'` may modify files under `specs/` (or configured `specDirs`). Tasks with `'implementation'`, `'repair'`, `'verification'`, missing, or unknown roles receive a non-overridable `'deny'` decision (`spec-write-fence-deny`).
   - Resolves relative paths, dot-dot segments, case-insensitive path variations (`SPECS/`, `Specs/`), existing symlinks, symlinked directories, and dangling symlinks via `realpathNearest` (`isSpecPath`).
   - Inspects `write`/`edit` tools, `shell` commands (redirections, command substitutions, globs, non-read-only commands), `git` write verbs targeting spec paths, and arbitrary/MCP tool string arguments while permitting read-only inspection (`read`, `cat`, `rg`, `ls`, `git diff`, etc.).
   - Even for `'spec-author'` executions, writing `status: approved` or `status: retired` to a spec manifest is denied (`spec-approval-human-only-deny`), preserving human-only spec approval.

2. **Layer A — Worktree & OS Sandbox Fencing (`packages/core/src/services/worktreeManager.ts`)**:
   - Added `applySpecReadOnlyFence`, `verifySpecReadOnlyFence`, and `releaseSpecReadOnlyFence` on `WorktreeManager`, invoked automatically during `createWorktree` for any non-`'spec-author'` role.
   - Applies `chmod -R a-w` (without following symlinks) to `specs/`, records directory `(dev, ino)` identities to detect tampering or replacement, generates `bwrap` (`--ro-bind`) and macOS Seatbelt (`(deny file-write* (subpath ...))`) rules, and sets `requiredIsolation: 'os'` so unsandboxed execution fails closed (`isolation-unavailable`).

3. **Layer B — Merge & Integration Gate (`packages/core/src/services/verifiedIntegrationCoordinator.ts`)**:
   - Added `checkSpecWriteFence` and wired it into `VerifiedIntegrationCoordinator.plan()`.
   - Diffs the candidate branch's actual git commit history (`--no-renames`) against its merge base with the target branch (ignoring agent-supplied manifest claims) and consults the trusted `resolveTaskRole` callback.
   - Rejects any branch from a non-`'spec-author'` task that touches `specs/**` with a `SPEC_WRITE_FENCE` blocker.
   - Verifies that `'spec-author'` branches leave modified spec manifests in `draft` or `reviewed` status, blocking self-approval (`approved`), self-retirement (`retired`), or deletion of approved specs.

4. **Policy Facade & Assurance Wiring (`packages/policies/src/index.ts`, `packages/assurance/src/fencing.ts`)**:
   - Exposed `registerSpecFence`, `evaluateSpecFence`, `isSpecAuthorRole`, and `specWriteFenceBlocker` in `@wazir/policies`.
   - Created `packages/assurance/src/fencing.ts` (`fenceTaskWorkspace`, `verifyTaskWorkspaceFence`, `checkSpecMerge`, `createTaskRoleResolver`) composing the core services via dependency injection without circular package dependencies.

5. **Unit & Integration Tests (`packages/assurance/src/__tests__/fencing.test.ts`)**:
   - Added 9 comprehensive test suites covering `PolicyEngine` tool/shell/git/MCP classification, relative path and symlink resolution, `WorktreeManager` `chmod -R a-w` permissions and `bwrap`/Seatbelt rule generation, `VerifiedIntegrationCoordinator` out-of-band edit rejection (`SPEC_WRITE_FENCE`), and `'spec-author'` draft/reviewed editing vs. human-only approval enforcement.
