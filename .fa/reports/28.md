## Notes / decisions
- **Hash algorithm:** `content_hash` now matches `computeSpecHash()` in `packages/assurance/src/registry.ts`, which is sha256 over the canonical sorted-key JSON of the parsed manifest without `content_hash`. My original file-digest algorithm did not match, so `SpecRegistry` rejected the manifest. `compute_hash.py` now ports the registry's restricted YAML parser and canonicalisation. Its output equals the TS result, and `parseSpecManifest` plus `SpecRegistry('specs')` both accept the manifest. Trade-off: the spec hash no longer covers artifact bytes. Those are pinned by the assurance record's `artifactHashes`.
- **Mutants:** in Alloy, the mutant is the `crossUnguarded` action (stop guard removed), checked by `NoCrossOnRedMutant`. In Z3, `mutant` doubles the dilemma-zone threshold (one guard relaxed). My first Z3 mutant (dropping the margin) made the guard *stricter* and came back PROVED, so I replaced it.
- The manifest lists only `WitnessStop` and `NoCrossOnRed` as Alloy commands. The negative-control `NoCrossOnRedMutant` is in the `.als` file but should be run as a separate step that is expected to fail.
- z3 Python bindings are present for `/opt/homebrew/bin/python3` only (not the default miniforge `python3`). Adapters should pick their interpreter with this in mind or report `NOT_RUN`.
- No `manifest.json` was added, so there is only one source of truth.
- Everything here is a toy model, not a certified braking or traffic-law model.

## Alignment fixes (after the Agent 30 audit)
- `manifest.yaml` `content_hash` now equals the registry `computeSpecHash` (see above).
- `stopping_envelope.py`: `--candidate` defaults to `$WAZIR_RED_SIGNAL_CANDIDATE` or `guarded`, so `Z3Adapter` (which passes `metadata.args`, empty by default) no longer hits an argparse error. The output carries `vacuity_probe` and `vacuityProbe` as `{passed, assumptionsSat, preconditionSat, details:{assumptions, precondition}}`. Every value is **computed from the two solver checks**, not hard-coded, so a vacuous spec still reports `passed: false`. On the PROVED/COUNTEREXAMPLE paths all of them are `true`.
- Checked through the real `Z3Adapter` (`tools/z3-venv`, z3 5.3.1): no args gives `BOUNDED_PASS`, because the output includes `scope` and the adapter therefore downgrades PROVED. `--candidate buggy` gives `COUNTEREXAMPLE`.
- Known gap (not fixed, adapter-side): the adapter driver re-raises `SystemExit` codes other than 0/2. A VACUOUS (exit 4) or UNKNOWN (exit 3) run therefore surfaces as `ERROR`, not `INCONSISTENT_ASSUMPTIONS`/`UNKNOWN`.
