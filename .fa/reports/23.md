# Agent 23 Report — Scheduler Feasibility: Hosts Advertise Installed Tools

## Summary

Implemented Phase 5 formal assurance scheduler integration (`packages/assurance/src/scheduler-feasibility.ts`, `packages/core/src/services/scheduler.ts`, and `packages/scheduler/src/index.ts`), extending the scheduler's feasibility set $F(t)$ with pinned formal tool capabilities, DGX/GX10-class host preference for heavy obligations, model-router bypass for solver tasks, and explicit `NOT_RUN` unschedulable diagnostics.

## Changes Made

1. **Extended Host Feasibility Set $F(t)$ (`packages/core/src/services/scheduler.ts`, `packages/assurance/src/scheduler-feasibility.ts`)**:
   - Canonicalized formal tool capabilities (`tool:z3`, `tool:alloy`, `tool:dafny`, `tool:scenic`, `tool:verifai`, `tool:verifai.simulator`, `tool:gam`).
   - Added `advertiseHostToolCapabilities()` to map `ToolAvailability` / `wa assure doctor` probe outcomes into advertised host capabilities.
   - Updated both `Scheduler.scheduleComputer` and `Scheduler.scheduleToolHost` (plus `evaluateHostFeasibility` / `computeFeasibilitySet`) so a `Computer` host is in $F(t)$ if and only if it advertises every required pinned tool capability alongside OS, architecture, GPU/CUDA, memory, and policy constraints. Hosted inference providers without a physical `Computer` identity are rejected when formal tool capabilities are required.

2. **DGX / GX10-Class Preference for Heavy Obligations**:
   - Added `isDgxClassComputer` / `isDgxClassHost` to detect DGX Spark / GX10 / GB10 / NVIDIA unified-memory hosts.
   - Added `isHeavyVerificationTask` / `isHeavyObligation` to classify VerifAI campaigns (`tool:verifai`, `tool:verifai.simulator`), Alloy obligations with scope bounds $\ge 6$, or tasks with `preferHostClass: 'dgx'` as heavy obligations.
   - Heavy obligations receive a $+10$ placement score bonus on DGX/GX10-class hosts while retaining non-DGX feasible hosts as fallbacks. Small Z3 checks (`isHeavyObligation === false`) run on any feasible host and prefer low-latency local hosts when available.

3. **Model-Router Bypass (`scheduleToolHost`)**:
   - Added `Scheduler.scheduleToolHost(task)` and updated `Scheduler.plan({ task })` so that when `task.type === 'verification'` (or `task.role === 'verification'`), Phase 1 `routeModel` and `ResourceRouter` are completely bypassed (`strategy: 'tool_bypass'`, `modelId: ''`, `resourceType: 'FORMAL_TOOL_EXECUTION'`).
   - Solver tasks require no LLM model, work even when `ModelRegistry` is empty, and consume zero model capacity or token budget.

4. **Explicit Unschedulable / `NOT_RUN` Outcome**:
   - When no host in $F(t)$ advertises the required tool capabilities, `scheduleToolHost` returns `{ status: 'NOT_RUN', verdict: 'NOT_RUN', missingCapabilities }` and `Scheduler.plan` throws `SchedulingError` annotated with `verdict: 'NOT_RUN'` and `missingCapabilities`.
   - `scheduleVerificationObligation` and `buildUnschedulableNotRunResult` produce a `VerificationResult` with `Verdict.NOT_RUN` and detailed per-host rejection reasons rather than silently skipping or dispatching to an incapable host.

5. **Comprehensive Unit & Integration Tests (`packages/assurance/src/__tests__/scheduler-feasibility.test.ts`)**:
   - 15 test cases covering tool capability normalization, doctor advertisement, $F(t)$ filtering, multi-capability partial mismatch rejection, DGX/GX10 host detection and scoring preference for VerifAI and large Alloy scopes, local host preference and fallback for small Z3 checks, model-router and `ResourceRouter` bypass with an empty `ModelRegistry`, and explicit `NOT_RUN` results when no host in the fleet has the required tool.
