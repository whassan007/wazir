## 0. Executive Summary & Architectural Contract

The Wazir V02 architecture transforms Wazir from a local/distributed task runner into a **hardened, verifiable execution control plane**. V02 delivers 10 canonical platform capabilities in a strictly ordered, dependency-respecting sequence.

```text
                           WAZIR CONTROL PLANE
┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│  Task → Requirements → Policy Engine → JobGraph                             │
│                           │                                                 │
│                           ▼                                                 │
│                      Agent Router                                           │
│                           │                                                 │
│                           ▼                                                 │
│                      Model Router                                           │
│                           │                                                 │
│                           ▼                                                 │
│                  Computer Scheduler ◄──── Resource Governance               │
│                           │                                                 │
└───────────────────────────┼─────────────────────────────────────────────────┘
                            │
                            ▼
                   ┌──────────────────┐
                   │  Worker Runtime  │ ◄──── Execution Recovery
                   └────────┬─────────┘
                            │
               ┌────────────┼────────────┐
               ▼            ▼            ▼
            Runtime       Tools         MCP
               │            │            │
               ▼            ▼            ▼
             Model    Secret Broker  Connectors
               │            │            │
               └────────────┼────────────┘
                            │
                            ▼
                        Execution
                            │
       ┌────────────┬───────┴───────────┬──────────────┐
       ▼            ▼                   ▼              ▼
   Artifacts      Events            Evaluation     Resources
       │            │                   │              │
       ▼            ▼                   ▼              ▼
   Artifact     Execution             Test          Resource
  Provenance   Intelligence       Intelligence     Governance
       │                                               │
       ▼                                               ▼
  Supply Chain Security ──────────────────────► Execution Chaos
```

### 0.1 Non-Negotiable Architectural Rules

1. **The control plane makes decisions; workers execute authorized decisions.**
2. **Models are never authorities.** A model cannot certify its own output, approve policy exceptions, or select test subsets without independent verification.
3. **No tool or agent bypasses the Policy Engine.** Every action request is evaluated before process spawning or API invocation.
4. **Every execution has durable identity and immutable lineage.**
5. **Every artifact has deterministic provenance computed from byte content.**
6. **Failures are explicit state transitions, never silent or implicit retries.**
7. **No silent model, runtime, or computer fallback.** Fallbacks must be configured explicitly in task policy.
8. **Secrets never enter model context, prompts, blocks, terminal logs, or session exports.**
9. **Resources are accounted for across all dimensions (CPU, RAM, VRAM, tokens, tool calls).**
10. **Chaos testing must verify resilience without causing uncontained side effects.**

## 1. Implementation Order & Dependency Topology

The 10 capabilities are sequenced in strict topological order to guarantee that no phase is implemented before its dependencies exist:

```text
Phase 1: Artifact Provenance
   │   (Establishes durable artifact identity, hashing, and execution graph)
   ▼
Phase 2: Execution Recovery
   │   (Adds explicit failure taxonomy, idempotency tokens, and state transitions)
   ▼
Phase 3: Test Intelligence
   │   (Maps Git diffs & AST dependencies to tests, linking back to provenance)
   ├───┐
   ▼   ▼
Phase 4: Supply Chain Security       Phase 5: Worker Runtime
   │   (SBOMs, model digests)           │   (Hardened nodes, sandbox, lifecycle)
   │                                    ▼
   │                                 Phase 6: Secret Broker
   │                                    │   (Decoupled secret authority & redaction)
   │                                    ▼
   │                                 Phase 7: Connector Registry
   │                                    │   (Typed interfaces, rate limiting)
   └─────────────────┬──────────────────┘
                     ▼
         Phase 8: Resource Governance
                     │   (VRAM/RAM reservations, priority queueing, backpressure)
                     ▼
         Phase 9: Execution Intelligence
                     │   (End-to-end metrics, traces, derived throughput, cost)
                     ▼
         Phase 10: Execution Chaos
                         (Fault injection, automated resilience verification)
```

## Phase 2: Execution Recovery

### 2.1 Objective
Transform unexpected runtime, worker, model, and network failures into explicit, auditable, policy-governed state transitions.

### 2.2 Data Schemas (`packages/core/src/types/recovery.ts`)

```typescript
export type FailureCategory =
  | 'model_failure'
  | 'runtime_failure'
  | 'worker_failure'
  | 'computer_failure'
  | 'network_failure'
  | 'tool_failure'
  | 'mcp_failure'
  | 'policy_denial'
  | 'resource_exhaustion'
  | 'context_overflow'
  | 'timeout'
  | 'cancellation'
  | 'authentication_failure'
  | 'persistence_failure'
  | 'validation_failure'
  | 'unknown';

export type RecoveryAction =
  | 'retry'
  | 'resume'
  | 'reassign'
  | 'replan'
  | 'context_reduce'
  | 'fallback_model'
  | 'escalate_approval'
  | 'skip'
  | 'cancel';

export interface RecoveryPolicy {
  maxAttempts: number;
  backoff: 'fixed' | 'exponential';
  initialIntervalMs: number;
  maxIntervalMs: number;
  retryableErrors: FailureCategory[];
  allowWorkerReassignment: boolean;
  allowModelFallback: boolean;
  fallbackModels?: string[];
  allowContextReduction: boolean;
}

export interface RecoveryRecord {
  id: string;
  executionId: string;
  attemptNumber: number;
  failureCategory: FailureCategory;
  failureDetails: string;
  actionTaken: RecoveryAction;
  targetComputerId?: string;
  targetModelId?: string;
  timestamp: Date;
  idempotencyToken: string;
}
```

### 2.3 State Machine Definition
```text
           [RUNNING]
               │
      ┌────────┴────────┐
      ▼                 ▼
 [COMPLETED]       [FAILURE]
                        │
                        ▼
               [RECOVERY_PENDING]
                        │
       ┌────────┬───────┼────────┬────────┐
       ▼        ▼       ▼        ▼        ▼
    [RETRY]  [RESUME] [REASSIGN] [REPLAN] [WAITING_FOR_APPROVAL]
       │        │       │        │        │
       └────────┴───────┼────────┘        ▼
                        ▼            [CANCELLED]
                    [RUNNING]         (Terminal)
```
*Critical Invariant:* `CANCELLED` is strictly terminal and can never transition to `COMPLETED` or `RUNNING`.

### 2.4 Service Architecture & Package Locations
- **`packages/core/src/services/recoveryCoordinator.ts`**:
  - `classifyFailure(error: unknown): FailureCategory`
  - `determineAction(execution: ExecutionRecord, category: FailureCategory, policy: RecoveryPolicy): RecoveryAction`
  - `executeAction(executionId: string, action: RecoveryAction): Promise<void>`
  - `generateIdempotencyToken(executionId: string, attempt: number): string`
- **`packages/core/src/services/contextCompactor.ts`**:
  - Structured reduction: drop optional context parts -> summarize history -> re-budget (never silent truncation).

### 2.5 CLI Commands
```bash
wa executions retry <id> [--strategy retry|reassign|replan]
wa executions resume <id>
wa executions cancel <id>
wa recovery inspect <id> [--json]
```

### 2.6 Verification & Gate 2 Criteria
- [ ] Transient network and timeout errors trigger exponential backoff up to `maxAttempts`.
- [ ] Non-retryable errors (`policy_denial`, invalid syntax) fail immediately without retries.
- [ ] Worker crash/disconnect triggers `reassign` to a healthy node with active reservations released.
- [ ] Idempotency tokens prevent duplicated external tool calls on retry.

## Phase 3: Test Intelligence

### 3.1 Objective
Intelligently compute and run only the minimal set of tests impacted by code changes, backed by dependency analysis and confidence scoring.

### 3.2 Data Schemas (`packages/core/src/types/testIntelligence.ts`)

```typescript
export type TestSelectionMode =
  | 'full'
  | 'impacted'
  | 'targeted'
  | 'failed_only'
  | 'smoke'
  | 'security'
  | 'regression';

export interface TestSelectionDecision {
  mode: TestSelectionMode;
  selectedTests: string[];
  excludedTests: string[];
  confidence: number; // 0.0 - 1.0
  reasons: string[];
  riskLevel: 'low' | 'medium' | 'high';
  escalatedToFull: boolean;
  computedAt: Date;
}
```

### 3.3 Dependency Analysis & Selection Engine
- **`packages/core/src/services/testIntelligence/importGraph.ts`**:
  - Parses TypeScript/JavaScript AST to extract import statements and file dependencies.
  - Builds bidirectional dependency map (`file -> dependents` and `file -> dependencies`).
- **`packages/core/src/services/testIntelligence/selector.ts`**:
  - Consumes Git diff (`git diff --name-only HEAD~1` or working tree diff).
  - Traces changed files through import graph to identify candidate test files.
  - Evaluates confidence:
    - If `package.json`, `tsconfig.json`, or root configurations changed: confidence = 0.0 -> automatically escalates to `FULL`.
    - If dynamic imports or untraceable references detected: confidence penalized.

### 3.4 Integration with Agent Loop & Evaluation
- In `packages/agents/src/codingAgent.ts`:
  - The verification phase asks Test Intelligence for impacted tests:
    `const decision = await testIntelligence.select({ root, changedFiles, mode: 'impacted' });`
  - Runs selected test suite.
  - Provenance links test results to artifact modifications.

### 3.5 CLI Commands
```bash
wa test run [--mode impacted|targeted|full|failed_only] [--explain] [--json]
wa test impacted [--json]
```

### 3.6 Verification & Gate 3 Criteria
- [ ] Directly modified module triggers only its unit tests and immediate dependent test suites.
- [ ] Transitive imports across workspace packages correctly flagged.
- [ ] Root configuration changes trigger automatic escalation to `FULL`.
- [ ] Selection decision with confidence score and reasons recorded in execution record.

## Phase 5: Worker Runtime

### 5.1 Objective
Harden distributed worker nodes into isolated, remotely managed execution boundaries with explicit model lifecycle and process sandboxing.

### 5.2 Worker Architecture & Lifecycle
```text
           [DISCOVERED]
                │
                ▼
           [AVAILABLE]
                │
         loadModel()
                │
                ▼
           [LOADING] ──────► [LOAD_FAILED]
                │
                ▼
            [LOADED]
                │
         task assigned
                │
                ▼
            [IN_USE]
                │
        unloadModel()
                │
                ▼
          [UNLOADING]
                │
                ▼
           [AVAILABLE]
```

### 5.3 Process Sandboxing (`packages/tools/src/process.ts`, `sandbox.ts`)
- **Linux (`bwrap`)**:
  - Project directory mounted read-write.
  - Root `/usr`, `/bin`, `/lib` mounted read-only.
  - Dedicated isolated `/tmp`.
  - Network namespace dropped unless `networkAllowed: true`.
- **macOS (`sandbox-exec`)**:
  - Custom seatbelt scheme restricting file writes exclusively to project root and temporary workdir.
- **Fallback**:
  - Explicit configuration `WAZIR_SANDBOX=none` required to disable; mode stamped onto execution record.

### 5.4 Implementation of `loadModel` / `unloadModel`
- **`packages/runtimes/ollama/src/index.ts`**:
  - `loadModel(id)`: calls `/api/generate` with `keep_alive: "30m"`, empty prompt to force residency.
  - `unloadModel(id)`: calls `/api/generate` with `keep_alive: 0` to reclaim VRAM.
- **`packages/runtimes/lmstudio/src/index.ts`**:
  - `loadModel(id)`: calls LM Studio v1 model loading endpoint.
  - `unloadModel(id)`: calls LM Studio v1 model unload endpoint.
- **Observability**: Emits `model.loading` and `model.loaded` events with measured `durationMs`.

### 5.5 Mutual Authentication (`apps/api/src/auth.ts`, `packages/workers/src/worker.ts`)
- Workers sign requests with their durable SHA-256 worker token.
- API validates worker token against `KeyValueStore` (`auth:computer:<id>`).
- API validates computer hardware and heartbeat before accepting execution streams.

### 5.6 CLI Commands
```bash
wa worker start [--id <id>] [--api-url <url>] [--sandbox bwrap|sandbox-exec|none]
wa workers status <id> [--json]
wa workers load-model <computer-id> <model-id>
wa workers unload-model <computer-id> <model-id>
```

### 5.7 Verification & Gate 5 Criteria
- [ ] Explicit cold model load and explicit unload reclaim system/GPU RAM.
- [ ] Sandbox blocks path traversal attacks (`cat /etc/shadow` or writes to host files).
- [ ] Worker loss triggers clean task recovery on peer worker.
- [ ] Events `model.loading` and `model.loaded` are emitted and recorded.

## Phase 8: Resource Governance

### 8.1 Objective
Enforce fleet-wide multi-dimensional resource budgeting, reservations, priority queueing, and fair scheduling.

### 8.2 Resource Dimensions & Job Budgets (`packages/core/src/types/resource.ts`)

```typescript
export interface ResourceBudget {
  maxAgents: number;
  maxConcurrentExecutions: number;
  maxTurns: number;
  maxInputTokens: number;
  maxOutputTokens: number;
  maxExecutionTimeMs: number;
  maxToolCalls: number;
  maxMemoryGB: number;
  maxVramGB?: number;
}

export type PriorityClass =
  | 'critical'
  | 'high'
  | 'normal'
  | 'low'
  | 'background';

export interface ResourceReservation {
  reservationId: string;
  computerId: string;
  modelId: string;
  vramGB: number;
  ramGB: number;
  cpuCores: number;
  claimedAt: Date;
  status: 'active' | 'released';
}
```

### 8.3 Resource Governor Service (`packages/core/src/services/resourceGovernor.ts`)
- **Reservation Tracking**:
  - Manages active reservations per computer node.
  - Reconciles hardware capacity against `(hardware.memoryGB - load.memoryUsedGB - activeReservations.ramGB)`.
- **Scheduler Integration (`packages/core/src/services/scheduler.ts`)**:
  - Phase 2 `scheduleComputer()` checks both free RAM/VRAM and unreserved allocations.
  - If node has insufficient unreserved VRAM, placement fails or task is queued.
- **Priority Queue & Backpressure**:
  - When resources are saturated, tasks wait in `QUEUED` state.
  - Queue dispatch orders by `PriorityClass` (`critical` -> `high` -> `normal` -> `low`).
- **Automatic Reclamation**:
  - Reclaims reservations immediately on `execution.completed`, `execution.failed`, `execution.cancelled`, or worker loss.

### 8.4 CLI Commands
```bash
wa resources status [--json]
wa resources reservations [--json]
wa resources queue [--json]
```

### 8.5 Verification & Gate 8 Criteria
- [ ] Saturated nodes reject new concurrent tasks and place them in the priority queue.
- [ ] Tasks resume execution automatically as reservations are released.
- [ ] Task cancellation or failure immediately reclaims all reserved RAM and VRAM.

## Phase 10: Execution Chaos

### 10.1 Objective
Deliberately inject infrastructure, worker, model, network, and resource faults to verify control plane resilience, automated recovery, and data integrity.

### 10.2 Experiment Specification (`packages/core/src/types/chaos.ts`)

```typescript
export type ChaosTarget =
  | 'worker'
  | 'runtime'
  | 'model'
  | 'network'
  | 'resource'
  | 'control_plane';

export type ChaosFault =
  | 'kill_process'
  | 'hang_response'
  | 'inject_latency'
  | 'exhaust_vram'
  | 'corrupt_response'
  | 'restart_service';

export interface ChaosExperiment {
  id: string;
  name: string;
  target: ChaosTarget;
  fault: ChaosFault;
  targetId: string;
  durationSeconds: number;
  blastRadius: 'isolated_worker' | 'single_task';
  expectedRecovery: RecoveryAction;
  rollbackAction: string;
}
```

### 10.3 Chaos Engine (`packages/core/src/services/chaosEngine.ts`)
- **Safety Boundaries**:
  - Gated behind `--enable-chaos` and requiring explicit policy approval.
  - Active timeout guard automatically terminates experiments and triggers rollback.
- **Injections**:
  - Worker failure: abruptly drops worker heartbeat connection.
  - Runtime hang: injects artificial infinite latency in adapter mock/proxy.
  - Resource exhaustion: artificially claims remaining VRAM in governor.
- **Verification Assertions**:
  - Confirms execution transitions to `RECOVERY_PENDING`.
  - Confirms peer worker takes over task.
  - Confirms artifact provenance and git worktrees are preserved without corruption.

### 10.4 CLI Commands
```bash
wa chaos run <experiment.yaml> [--dry-run]
wa chaos list [--json]
wa chaos abort <experiment-id>
```

### 10.5 Verification & Gate 10 Criteria
- [ ] Sudden worker kill during task execution triggers automated reassignment and successful completion.
- [ ] Simulated control plane restart cleanly reconciles running tasks from store without data loss.
- [ ] Fault injection leaves artifact provenance and audit trail intact.
