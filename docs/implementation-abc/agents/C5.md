## 2. Qualification Architecture & Invariants Verified

The `crossHarnessRecoveryQualification.test.ts` suite implements a deterministic, side-effect-aware failure injection and recovery qualification harness (`runRecoveryQualificationSuite()`) spanning all **12 mandatory failure-injection scenarios** from Section 6:

1. **Kill a native agent during implementation (`runScenario1KillNativeAgent`)**:
   - Injects a hard process kill (`AFTER_TOOL_EXECUTION_BEFORE_PERSIST`, exit 137) after a confirmed file write (`src/moduleA.ts` at revision 1) and mid-dispatch of a second write (`src/moduleB.ts`).
   - Reconstructs state on a backup controller/agent, inspects physical disk to reconcile `call-s1-write-b` as `APPLIED`, creates an automatic handoff, resumes the same `executionId` on `native-coder-backup`, verifies at revision 2, and completes without repeating confirmed writes.
2. **Terminate an ACP subprocess (`runScenario2TerminateAcpSubprocess`)**:
   - Spawns a real Node.js child process speaking JSON-RPC over stdio to simulate an external ACP harness (`acp-codex-external`).
   - Captures a verified write (`src/acpFeature.ts` at revision 1), then sends `SIGKILL` to the live subprocess mid-turn after `acp/tool_started` for `call-acp-2`.
   - Reconciles `call-acp-2` as `NOT_APPLIED` from physical disk inspection, creates an automatic handoff to `native-harness-coder`, and completes the task at revision 2.
3. **Disconnect an eligible remote worker (`runScenario3DisconnectRemoteWorker`)**:
   - Simulates worker heartbeat expiration on `remote-worker-1` and runs `RecoveryManager.sweep()` to orphan the active execution.
   - Acquires a new lease (`epoch: 2`) on `remote-worker-2`, verifies that stale `remote-worker-1` (`epoch: 1`) is strictly fenced out via `StaleWorkerLeaseError`, materializes the content-addressed checkpoint onto `remote-worker-2` via `CheckpointService.materializeOnTarget()`, and completes the execution.
4. **Simulate provider rate limiting — HTTP 429 (`runScenario4ProviderRateLimiting`)**:
   - Classifies HTTP 429 via `classifyHttpFailure(429, ...)` as `'RATE_LIMIT'` (`isProviderRetryable === true`), records `retry.scheduled` and `retry.exhausted` events via `ExecutionEngine.recordProviderEvent()`, and steers execution onto `ollama-local` while preserving `executionId`, workspace revision, and accumulated token budget.
5. **Simulate model unavailability (`runScenario5ModelUnavailability`)**:
   - Transitions the primary model instance (`primary-coder-7b`) to `UNAVAILABLE` mid-task after revision 1.
   - Re-plans via `Scheduler.plan()` to deterministically select `backup-coder-14b`, steers the active execution, and finishes at revision 2 with all pre-crash work preserved.
6. **Interrupt a stream after partial output (`runScenario6InterruptStreamPartialOutput`)**:
   - Triggers `DURING_MODEL_STREAM` fault injection after `generation.started` and `generation.token` events but before any tool call dispatch.
   - Verifies `reconstructExecutionState()` reports `unresolvedToolCalls: []` and `planRecovery()` returns `action: 'resume'` at revision 1 with zero duplicate side effects.
7. **Restart the orchestrator after checkpoint persistence (`runScenario7RestartOrchestratorAfterCheckpoint`)**:
   - Persists execution state, checkpoints, and handoff records to an on-disk `JsonFileStore`.
   - Instantiates a fresh `ExecutionEngine`, `CheckpointService`, and `HandoffService` in a new process context (`pid2`), verifies dead-owner detection (`OWNER_PROCESS_EXITED`), restores checkpoint and handoff records with SHA-256 digest verification, and completes the execution.
8. **Attempt duplicate tool delivery (`runScenario8DuplicateToolDelivery`)**:
   - Attempts to dispatch the same mutating tool `callId` (`call-s8-mut-1`, `NON_IDEMPOTENT_WRITE`) twice during recovery.
   - Verifies `ExecutionEngine.recordToolStart()` rejects the duplicate dispatch with `TOOL_ALREADY_DISPATCHED`, and conflicting `recordToolCall()` payloads are rejected, ensuring the physical target file is mutated once.
9. **Restore a corrupted checkpoint (`runScenario9RestoreCorruptedCheckpoint` — Fail-Closed)**:
   - Tampers with file contents in a checkpoint snapshot and in the backing store envelope.
   - Verifies `CheckpointService.materializeOnTarget()` throws `CHECKPOINT_MATERIALIZATION_FAILED` and `CheckpointService.ready` throws `CHECKPOINT_DIGEST_MISMATCH` without touching the target directory.
10. **Resume after a workspace revision change (`runScenario10WorkspaceRevisionChangeAfterCheckpoint`)**:
    - Mutates the workspace after checkpoint creation and passing `BUILD`/`TEST` checks at revision 1, advancing the workspace to revision 2.
    - Verifies `reconstructExecutionState()` reports `verification.staleChecks > 0`, `inspectVerificationEvidence()` marks `BUILD` and `TEST` slots `STALE`, `ExecutionEngine.setStatus(..., 'completed')` rejects completion until fresh revision-2 verification is recorded, and completion succeeds after re-verification at revision 2.
11. **Attempt replay with insufficient remaining budget (`runScenario11InsufficientRemainingBudget` — Fail-Closed)**:
    - Exhausts token (`550 / 500`), tool-call (`2 / 2`), and model-request (`2 / 2`) budgets before interruption.
    - Verifies `planRecovery()` returns `action: 'terminate'` (`budget exhausted before recovery: modelRequests, toolCalls, tokens`) and refuses replay.
12. **Attempt recovery that would violate existing policy (`runScenario12PolicyViolatingRecovery` — Fail-Closed)**:
    - Attempts to route a `localOnly: true` / `dataClassification: 'sensitive'` task to a hosted provider (`openai`), dispatch a subagent, write outside `projectRoot` (`/etc/wazir-escaped.conf`), and run `sudo rm -rf /`.
    - Verifies `PolicyEngine` and `Scheduler` reject every violation fail-closed (`policy_violations === 0`).
