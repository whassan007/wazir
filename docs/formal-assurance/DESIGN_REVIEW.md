## Findings requiring action

1. **High — remaining requirement coverage and acceptance gaps (DESIGN §§2.1, 2.5, 2.7; build §§0–1, 3–5).** Section 2 now specifies adapters/probes, scheduling, repair, refinement, ledger, CLI and phase destinations; the earlier finding that these sections were absent is closed. Still missing are skill routing through existing context injection, preservation of bundle examples, an executable red-signal demonstration plan (including negative-control mutant), and phase-by-phase acceptance checks. Coverage limits in §2.5 address safety/legal claim exclusions, but do not explicitly cover every build non-goal. Complete the remaining coverage table items before approval.
2. **High — read-only fencing is conditional and bypassable (DESIGN §1.5; build §2.2).** An owning worker can restore file permissions after `chmod -R a-w`; shell policy cannot recognize arbitrary interpreter writes. Optional OS isolation therefore does not establish the claimed independent prevention layer. Require enforced read-only sandbox/container paths and fail closed when unavailable, using the existing isolation-compliance mechanism (REPO_MAP §1.3). Cover creation of absent specs directories, directory replacement, symlinks/path normalization, external harnesses, and copy-workspace fallback. Default missing/unknown roles to denied. Preserve the independent merge fence, deriving roles from trusted persisted tasks and preventing workers from selecting/escalating their own role. Test interpreter/chmod bypass and out-of-band edits, not only edit-tool denial.
3. **High — trusted dependency paths are ambiguous (DESIGN §1.2).** The layout places spec fencing helpers in assurance while policies re-exports them; assurance depends on core. Explicitly locate the authoritative role-aware fence in the existing policy implementation/facade, as requested, with no core→assurance dependency and no assurance↔policies cycle. Section 2.2 now explicitly locates scheduler feasibility and model-router bypass in core behind the scheduler facade, resolving that part of the earlier finding. Policy helper ownership remains ambiguous; do not introduce a reverse dependency or second policy engine.
4. **High — same-run probes and evidence provenance are stated but not enforceable from C0 alone (DESIGN §§1.3, 2.1, 2.3, 2.5; build §§2.1, 2.7).** `VacuityProbeResult` only carries `passed/reason/details`; `VerificationResult` has no explicit run/obligation/revision identity. Specify a trusted normalization/append boundary binding probe and result to the same obligation, input hash, spec hash, and revision. Reject missing/stale probes and missing required obligations before aggregation. A raw passing verdict must not bypass this boundary by calling the release gate directly.
5. **Medium — refinement provenance needs a trusted validation boundary (DESIGN §§1.3, 2.4; build §2.6).** Section 2.4 now requires pinned recompilation/byte comparison or a passing same-run refinement obligation, and separately reports model/implementation claims; this resolves the earlier absence of correspondence checks. C0 still accepts only a production mode in `capImplementationVerdict`. Specify who validates compiler identity, verified-source and production hashes, proof identity and exact revision before calling it; require NOT_VERIFIED for missing/mismatched provenance. Record that evidence so an implementation-authored mapping cannot grant itself proof status.
6. **Medium — native-outcome mismatch (DESIGN §1.3 versus C0 verdict.ts).** Design maps Scenic `sampling_exhausted` to NOT_FALSIFIED; C0 maps it to UNKNOWN. Resolve deliberately: successful completed search without violation is NOT_FALSIFIED; incomplete/failed generation is UNKNOWN (or ERROR as appropriate). Neither is a formal pass. Document exact outcome semantics and fixtures.
7. **High — ledger validation and append are not yet atomic (DESIGN §2.5; build §2.7; REPO_MAP §2.2).** Section 2.5 adds existing ExecutionEngine lease validation, revision checks and a file lock or head-hash CAS. Checking the lease first and serializing only ledger appends leaves a race: ownership/revision can change between validation and append. Specify one fenced transaction/critical section covering lease validity, revision and chain head, coordinated with lease takeover and revision updates; identify the actual durable-store primitive. Include worker/epoch/token/expiry validation, concurrent append/takeover tests, crash recovery and partial JSONL writes. Hash-chain tamper tests do not establish lease fencing. A locally valid chain also cannot detect deletion of its final entries without an independently trusted head/checkpoint; define the threat boundary or add such an anchor.
8. **Medium — holdout freshness and repair termination are underspecified (DESIGN §2.3; build §2.5).** Persisting a failed holdout witness as a regression makes it repair evidence. The deterministic partition alone does not explain how the next final campaign obtains seeds unused during repair. Specify fresh withheld seeds per attempt and prevent their disclosure until evaluation. Persist the repair budget across replacement nodes/restarts and define how exhaustion bypasses ordinary orchestrator retries, so returning no replacement tasks really terminates at k. Test holdout failure → regression → repair → fresh final holdout, including restarts and concurrent property failures.
9. **Medium — record completeness and level mapping need explicit rules (DESIGN §§2.3–2.6; build §§2.1, 2.7–2.8).** Selecting entries by component/commit is insufficient to reject omitted obligations, old spec hashes, or superseded attempts. Reconcile the expected approved-spec/obligation set with current normalized results, including regressions and holdout; missing entries must block release. Define GAM's record level (absent from §2.5's tool mapping), component aggregation, and gate inputs: passing formal evidence plus NOT_FALSIFIED may pass C0's gate, whereas passing only their weakest-link aggregate would fail. Tool/property CLI filters must not silently reduce release requirements. Define deterministic selection of current results while retaining historical counterexamples.

## C0 decision

**No verdict enum changes are needed.** All required verdicts, tools, manifests, refinement modes, ledger and record shapes exist. No edits to C0 are made by this review.

Recommend additive, coordinated contract clarification before dependent implementations settle: typed run/probe/revision identity; validated refinement provenance (compiler version, hashes, proof reference); and ledger ownership identity matching existing worker/epoch/token/expiry claims. C0's optional numeric `LedgerEntry.fencingToken` is not by itself the existing execution lease's complete claim. Metadata can carry transitional fields, but the trusted boundary must require and validate them. Preserve source compatibility; do not force adapter workers to invent competing contracts.

C0 verdict.ts already blocks PROVED for Dafny trusted-base gaps (default downgrade to BOUNDED_PASS), caps formal implementation passes for contract_tests/none, rejects NOT_FALSIFIED promotion, and aggregates weakest link. These are observed code statements, not executed test results. A downgrade still requires its own passing probe. Decide/document whether gap-bearing Dafny evidence may gate as bounded evidence; the build spec explicitly requires blocking PROVED, not a blanket prohibition on every downgraded verdict.
