CONFIRMED DEFECT (P0 — execution reliability / crash)
-------------------------------------------------------
Repro: `wa run "What is 19 + 24? ..."` while the shared ~/.wazir/wazir.json
file lock was held by a concurrent `wa run` process. Result: the lock wait
timed out after 10s and the CLI exited via an unhandled-rejection crash
report (crash-2026-10-18T02-10-21-896Z.log), instead of a clean task
failure.

Root cause: apps/cli/src/run.ts had three `engine.executions.recordError`/
`recordEvent` write calls that were not defensively caught, while a sibling
call at line ~799 in the same file already was, with the comment "Best
effort: when the error *is* a rejected write, recording it would rethrow."
The inconsistency meant lock contention (or any store write rejection)
during these specific code paths escaped as a raw rejection:
  - apps/cli/src/run.ts: `case 'phase':` recordEvent (line ~771) — fires on
    every agent phase transition, every task.
  - apps/cli/src/run.ts: `case 'error':` recordError (line ~786) — fires on
    every tool/agent error.
  - apps/cli/src/run.ts: delegated-baseline-failure recordError (line ~835)
    — this one runs AFTER the function's main try/catch/finally has already
    closed, so nothing in the function could catch a rejection there; this
    is the most severe of the three, since the existing `storageError` /
    `persistenceError` guard at line ~822 only catches failures that
    happened *before* this point, not a fresh failure at this write.

Fix applied: wrapped all three awaited calls with `.catch(() => undefined)`,
matching the established pattern already used elsewhere in the same file.
No behavior change on the success path; on a lock-contended/rejected write,
the task now completes with its real result/errors instead of crashing the
whole CLI process.
